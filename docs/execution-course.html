Umicom C
Compiler and runtime learning series

From source code to useful feedback

This short course introduces compilers, interpreters, bytecode and garbage collection through the code currently available in Umicom C. You need no previous compiler knowledge. The practical sections assume Windows PowerShell, a text editor, CMake, Ninja and a C23-capable GCC installation. Use the existing build guide to establish those tools first.

Umicom C currently implements a bounded integer language shaped like C. It is not a complete C23 compiler, Java implementation or BASIC compiler. A successful example demonstrates its documented subset, not an entire application platform.

1. Source, machines and compilation

A source file is text describing a computation. The CPU executes machine instructions, which are numeric encodings understood by a particular processor. Assembly language gives human-readable names to those instructions. A compiler translates source into another representation. It may emit machine code directly; a separate text assembly file is not compulsory.

→

→

→

An interpreter executes a representation of the program. A virtual machine, or VM, defines a software instruction set. It need not emulate a complete computer. Umicom's current VM works with checked signed integers and bounded storage. The host compiler builds the VM itself into a native executable.

TinyCC demonstrates a different useful route: rapidly compile C into native code and execute it through a command or embeddable library. Its compile-and-run behavior is not bytecode interpretation. Its documented C support must be checked independently from Umicom's C23 goals.

FreeBASIC illustrates the separation of a language compiler, runtime libraries and declarations for other libraries. We can learn from that architecture without copying its implementation. A runtime supplies operations the generated program needs; a different source syntax does not eliminate that need.

Exercise: Explain why a Windows executable cannot simply be copied into a freestanding RISC-V Kernel and run. Answer: processor instructions, executable format and available system services can all differ.

2. Catch mistakes before a full build

A build commonly includes preprocessing, compilation and linking. Preprocessing handles directives such as includes; compilation checks and translates individual source units; linking resolves references between object files and libraries. Packaging, installation and tests add more work. Measure which stage takes hours before replacing the compiler.

Create a scratch folder. In a text editor save this as early.c. The semicolon is deliberately missing.

int main(void) {
    return 42
}

Open PowerShell in that folder. A command is an instruction to a tool. The following command asks GCC to check C23 syntax and issue common warnings without generating an executable:

gcc -std=c23 -Wall -Wextra -Wpedantic -fsyntax-only early.c

Expect a diagnostic near the closing brace or return statement. Add the missing semicolon and rerun. The command should finish without that diagnostic. Exact wording depends on the compiler. If PowerShell cannot find gcc, repair the toolchain PATH using the setup guide before proceeding.

GCC documents these diagnostic options. A syntax-only pass does not link libraries or exercise code. In a real project it needs the same include paths, macros, language standard and target options as the normal build. Reuse the project's compilation settings; a bare command on a complex Framework source may only report missing configuration.

AddressSanitizer is a separate native instrumentation route. Use it in a compatible toolchain and run meaningful inputs. Merely enabling a flag is not evidence that no leak or memory error exists.

3. Step through a small program

Save this complete program as lesson.uc in your Umicom C working directory:

int main(void) {
    int answer = 40;
    answer += 2;
    return answer;
}

int declares an integer. answer names a value. += 2 adds two and stores the result. return completes this program with a result. Braces group statements; semicolons terminate them.

  1. Build the CLI using the debugger guide.
  2. Run ./build/debug/bin/umicom-c.exe check lesson.uc. Check reports source admission; it does not execute the return value.
  3. Run ./build/debug/bin/umicom-c.exe debug lesson.uc.
  4. Type where, then step. Observe one operation.
  5. Type line, then locals. Repeat to observe the slot change.
  6. Type continue. Expect Result: 42.

A source line can produce several VM operations. The line command groups physical source coordinates rather than complete C statements. The debugger compiles the whole input before beginning; it does not incrementally accept new C declarations at the prompt.

Now replace the return expression with answer / 0. The source may compile, but execution stops on division by zero. A failed step leaves machine state unchanged. Read the diagnostic before looking for a result. Use quit to cancel a paused session without completing it.

4. Compile once into bytecode

Bytecode is a defined sequence of VM operations. Unlike a host C structure written directly to disk, a portable wire format specifies its layout and rejects unsupported versions. Umicom's decoder checks the bounded program before execution.

./build/debug/bin/umicom-c.exe compile lesson.uc lesson.umcb
./build/debug/bin/umicom-c.exe inspect-bytecode lesson.umcb
./build/debug/bin/umicom-c.exe debug-bytecode lesson.umcb

Use a new output filename if an artifact already exists; preserve old results for comparison. Bytecode stores source offsets but not the entire source text. Without source text, line stepping falls back to one instruction. Read the wire format before designing an interchange tool.

A JVM-style design needs more than compact instructions: verification, typed values, call frames, exceptions, references and library contracts must agree. The JVM specification is a useful architectural reference, not a claim that Umicom implements the JVM.

Exercise: Can a bytecode pass prove a native GTK window will open? Answer: no. The bounded VM does not execute the GTK runtime or its platform dependencies.

5. Why collection needs ownership rules

Memory is storage. A native C pointer refers to an address; losing track of its lifetime can lead to stale access. A managed handle is an identifier checked by an arena. The new optional heap has 32 bounded objects, each with payload bytes and explicit references.

A root identifies an object the caller still needs. Marking follows references from roots. Sweeping clears unreachable objects. Two objects that point to each other still become collectible when neither is reachable from a root.

  1. Read managed_cycle.c.
  2. Locate the two allocations and check the error handling.
  3. Find the two edges forming a cycle.
  4. Find collection with one root: zero objects are collected.
  5. Find collection with no roots: two are collected.
  6. Find the old-handle read: it must be refused.

Run the example through the commands in managed objects. This is a separate native SDK library. The integer VM has no managed-object instructions yet. A collector cannot automatically repair arbitrary C pointer arithmetic, close files, release GPU allocations or make an omitted root safe.

6. Tags select a language, not its semantics

The experimental scanner recognizes <?java ... ?>, <?basic ... ?>, <?c23 ... ?> and <?umicom ... ?>. Run:

./build/debug/bin/umicom-c.exe regions examples/language_regions.umc

Read its classification-only notice. The scanner finds spans; it does not compile these languages. Try the ordinary check command on the same file: rejection is expected. This prevents a display feature being mistaken for executable support.

Before implementing calls between languages, define integer sizes, string encoding, error propagation and ownership. An application binary interface, or ABI, defines how compiled pieces exchange values and control. Begin with independent modules and a narrow ABI. Java class loading and reflection cannot be preserved by replacing tags with C text. Read the envelope contract for scanner limitations.

7. Make the small development loop measurable

Do not rebuild every product after every one-line edit. In a configured CMake tree, build the affected target and run its related tests. Full integration checks still belong before release.

cmake --build build/debug --target umicom-c-test-machine --parallel 2
ctest --test-dir build/debug -R "umicom.c.machine" --output-on-failure --no-tests=error

Record the source revision, changed files, compiler, build type, target, elapsed time and result. Compare the same operation before and after a change. Distinguish a warm incremental build from a clean build; cached inputs can make timings very different.

TinyCC's public home page contains a historical benchmark using an old GCC release and Pentium 4 hardware. It is not evidence for present-day speedups on Umicom projects. Bytecode can shorten some execution loops, but it does not eliminate preprocessing, frontend work or native integration. Measure each claim.

Final exercise: deliberately introduce a syntax error, an execution error and a stale managed handle. Write down which layer catches each. Then explain why passing all three checks still does not certify an entire desktop application.
